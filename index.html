SRE Brain • GKE Observability Demo

GKE → Prometheus → Monarch + Cloud Logging → Automon

A practical, command-driven SRE observability demo on Google Kubernetes Engine. The workload generates controlled incidents, Google Cloud collects metrics and logs, and a custom Python Automon layer correlates the signals and produces a diagnosis.

What this demonstrates

  • Application telemetry on GKE
  • Managed Service for Prometheus
  • PromQL queries through Google Cloud
  • Cloud Logging queries
  • Metric + log correlation
  • Rule-based incident diagnosis

Important Monarch distinction: Monarch is Google's internal distributed time-series backend. This demo does not directly access an internal Monarch database. It queries managed time-series data through supported Google Cloud / Managed Service for Prometheus interfaces.

2. What each component does

GKE

Kubernetes platform where the payment API runs. The demo uses the sre-demo namespace.

Payment API

Python incident simulator. It exposes Prometheus metrics on port 8000 and prints structured JSON logs.

Managed Service for Prometheus

Google-managed Prometheus-compatible metrics collection and query service. Metrics can be queried with PromQL.

Monarch

Google's distributed time-series backend. For this project it is the conceptual backend behind the supported managed metrics query path.

Cloud Logging

Collects the GKE container logs and lets us filter ERROR/CRITICAL events and application messages.

Automon

Custom Python SRE Brain. It queries metrics, reads incident logs, extracts signals, correlates them and emits a rule-based diagnosis.

Useful PromQL

# Request rate
rate(payment_requests_total[5m])

# Error rate
rate(payment_errors_total[5m])

# Error percentage
100 * rate(payment_errors_total[5m])
/
rate(payment_requests_total[5m])

# Average latency
rate(payment_request_latency_seconds_sum[5m])
/
rate(payment_request_latency_seconds_count[5m])

# P50
histogram_quantile(
  0.50,
  sum(rate(payment_request_latency_seconds_bucket[5m])) by (le)
)

# P95
histogram_quantile(
  0.95,
  sum(rate(payment_request_latency_seconds_bucket[5m])) by (le)
)

# P99
histogram_quantile(
  0.99,
  sum(rate(payment_request_latency_seconds_bucket[5m])) by (le)
)

# Incident phase
payment_incident_phase
Counter note: payment_requests_total and payment_errors_total are counters. They increase over time and can reset after a process restart. Rates over a window are generally more useful for incident analysis.

6. Cloud Logging — test from Cloud Shell

Read recent logs from the namespace

gcloud logging read \
'resource.type="k8s_container" AND resource.labels.namespace_name="sre-demo"' \
--limit=10 \
--format="table(timestamp,severity,jsonPayload.service,jsonPayload.message)"

Read ERROR and CRITICAL logs

gcloud logging read \
'resource.type="k8s_container"
 AND resource.labels.namespace_name="sre-demo"
 AND (severity="ERROR" OR severity="CRITICAL")' \
--limit=20 \
--format="table(timestamp,severity,jsonPayload.service,jsonPayload.message,jsonPayload.incident_phase)"

Find database-related failures

gcloud logging read \
'resource.type="k8s_container"
 AND resource.labels.namespace_name="sre-demo"
 AND jsonPayload.message:"database"' \
--limit=20 \
--format="json"

Why use both metrics and logs?

Metrics

Quantify service behavior: traffic, error rate, latency and current incident phase.

Logs

Provide application context: database timeout, retry, connection-pool exhaustion and other events.

Correlation

Automon combines both signal types instead of treating an isolated metric or log as the whole incident.

9. Recommended live demonstration

  1. Show the GKE cluster and incident-api pod.
  2. Show PodMonitoring and explain that the application metrics are being collected.
  3. Run the PromQL request query and show the returned series.
  4. Run the error-rate query and explain counters versus rates.
  5. Show Cloud Logging and filter ERROR/CRITICAL events.
  6. Explain: metrics quantify degradation; logs provide application context.
  7. Run Automon.
  8. Wait for LATENCY_SPIKE, then ERROR_SPIKE, then CRITICAL.
  9. Run Automon again and show the correlated signals and diagnosis.
  10. Wait for RECOVERY and show that the service signals improve.
The SRE story:
Metrics answer "How bad is the service?"
Logs answer "What is the application reporting?"
Automon answers "Which signals correlate, and what incident does the evidence suggest?"
